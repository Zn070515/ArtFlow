# M15.5 Incident / Recovery 设计（2026-11-14）

## 0. 状态

Accepted for implementation, first vertical slice: incident + recovery.
Post-event feedback is a follow-up slice in the same milestone.

## 1. 背景

Live 已经能改分、平局裁决、撤销发布、重排节目，但没有一个**事故对象**把现场问题
记录下来：谁发现的、影响哪个节目/选手/回合、谁在处理、何时解决、为什么重开。
任务和审计能间接承载，但组织者在现场需要一条清晰的“当前事故”视图。

本 slice 新增 `incident` capability：

- 事故的完整生命周期（open → acknowledged → resolved，resolved 可 reopen）；
- 与活动、mode、可选业务对象（节目条目/表演/回合/报名）关联；
- Ops 事故面板与 Live 只读摘要；
- 所有变更走单写路径（receipt/audit/fact/outbox + OCC）。

## 2. 领域模型

### 定义

`incident` 没有可配置定义（`emptyDefinition` 即 `{ schemaVersion: 1 }`），
能力本身提供固定分类：

```ts
IncidentSeverity = "low" | "medium" | "high" | "critical"
IncidentCategory = "participant" | "judge" | "stage" | "technical" | "safety" | "other"
IncidentStatus   = "open" | "acknowledged" | "resolved"
```

### 运行时事实

表 `incident`：

| 列 | 说明 |
| --- | --- |
| id | `incident_<hash>` |
| activity_id | 所属活动 |
| mode | `test`/`rehearsal`/`formal`，操作事实分区 |
| severity/category | 分级与分类 |
| status | open/acknowledged/resolved |
| title/detail/location | 现场描述 |
| related_type/related_id | 可选：`schedule_entry`/`performance`/`round`/`registration` |
| assignee_id | acknowledge 时写入 |
| resolution | resolve 时必填 |
| opened_by | 创建人 |
| revision | OCC |
| created_at/updated_at | 时间 |

### 命令

- `incident.open`：title 非空、severity/category 合法、mode 合法；
- `incident.acknowledge`：仅 open → acknowledged，写入 assignee；
- `incident.resolve`：open/acknowledged → resolved，resolution 必填；terminal；
- `incident.reopen`：仅 resolved → open，reason 必填，保留历史审计。

所有命令要求 `incident.manage`，活动必须 active；`expectedRevision` 不匹配返回
`STALE_REVISION`；resolved 的普通更新被拒绝，只能 reopen。

### 读面

- Ops：`GET /api/activities/:id/incidents`，access `incident`；
- 支持 severity/status/mode 过滤（客户端过滤即可，读模型返回当前活动全部事故）；
- Live：只读摘要（open/acknowledged 数量与最新几条），不成为第二 authority。

## 3. 产品面

| 面 | 交付 |
| --- | --- |
| Studio | Pack 可选开关“是否需要现场事故记录？”；无结构化定义 |
| Ops | `IncidentCard`：打开事故、确认、解决、重开；severity/status 徽章 |
| Live | `IncidentSummary`：未解决事故数量与最新标题 |
| Portal | 无公开面（事故内部可见） |

Stage Show / Singer / Review Packs 增加可选问题，默认关闭；启用后在 Ops 出现卡片。

## Test architecture

**Contracts and capabilities touched**

新增 `incident` capability（manifest、empty definition、registry）和 `incident` 表；
不修改既有 capability 语义。`incident` 读级别加入 `ReadAccess`。

**Consumers and read models**

Ops `IncidentCard`、Live `IncidentSummary`；Consumer Graph 中四条 mutation route
由 Web client 消费；`IncidentOpened/Acknowledged/Resolved/Reopened` 事件在
`dynamic-dependencies.json` 声明为 Ops 读模型消费边。

**Lifecycle, terminal guards, and mode isolation**

- open → acknowledged → resolved；resolved 是终态，普通命令拒绝，reopen 是唯一出口；
- 每次命令用 `expectedRevision` 做 OCC；
- mode 由命令输入校验（test/rehearsal/formal），读面按 mode 过滤；
- 事故不改变任何其他 capability 的 gate（只做观测与恢复记录）。

**Adapters**

不新增 contract-tools lifecycle adapter：事故是单对象状态机，由
`incident-service.test.ts` 用真实 PostgreSQL 覆盖；在 adapter coverage 中给出具体豁免理由。

**Fault and recovery cases**

- stale revision；
- 对 resolved 事故 acknowledge/resolve → `INVALID_TRANSITION`；
- resolve 缺 resolution → `INVALID_INPUT`；
- reopen 缺 reason → `INVALID_INPUT`；
- 非 `incident.manage` 的 actor → `FORBIDDEN`；
- 非 active 活动 → `ACTIVITY_NOT_ACTIVE`；
- reopen 后 status/open 与 revision 正确，历史审计保留。

**Why existing tests are insufficient**

任务/审计/诊断没有事故对象，也没有“确认/解决/重开”的产品路径；现有测试无法
证明生命周期、OCC 和权限边界。

**Anti-bloat decision**

复用 `executeCommand`、receipt/audit/outbox、OCC 与 `StatusBadge`/`Card` 组件；
不新增事件总线、不复制任务能力，不把事故塞进 tasks。

**Focused gates**

domain `incident` test、runtime `incident-service` test、API `incident` test、
Web `IncidentCard` test、`graph:check`、`audit:check`、`schema:check`、
`tests/gates`、Playwright `e2e/incident.spec.ts`。
