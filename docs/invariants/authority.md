# AUTH — 写权限、所有权与访问边界

**原则**：权限不是视图里的一个 `if`，而是这个聚合所有写路径的闭包；模板和
按钮只是 UX，永远不是授权边界。

v1 证据：43 条权限/ORM 类 fix，高频词 `authority 33`、`enforce 26`、`access 14`。

---

## AUTH-01 一个聚合只有一个写命令

**规则**：聚合的创建、修改、删除只能通过领域 command 完成；仓储不向调用方
暴露通用的 `save/update/delete`。

**为什么**：每一条额外的 ORM 写路径都会绕过 command 内的状态、权限与审计
检查。v1 先后堵过 instance `save`、`QuerySet.update/delete`、`bulk_create`、
`bulk_update`、`_base_manager`、raw delete 和 Django Admin。

**必须攻击的形状**：

- 直接构造模型并 `save()`；
- 用 queryset 批量 `update` / `delete`；
- `bulk_create(update_conflicts=True)` 覆盖受保护行；
- 通过 base manager 或 raw SQL 绕过默认 manager；
- 在 Admin 里改字段后保存。

**Plus 要求**：写模型不暴露公开 mutator；所有写请求进入 command bus；command
内部做授权、状态校验、OCC 和审计。

---

## AUTH-02 授权按 scope 显式授予，并且只在 command 内开启

**规则**：需要绕开普通守卫的系统操作必须携带显式 authority scope；scope 由
command 在最小作用域内开启，调用方不能自行声明。

**为什么**：v1 用 `authority_write(scope)` 处理冻结、结果核定、结果发布、
测试数据清理等合法例外。没有 scope 的路径一律 fail closed。

**必须攻击的形状**：

- 在 scope 外调用受保护写；
- 伪造 scope 名称或嵌套 scope；
- 通过异步/线程把 scope 泄漏到其他请求。

**Plus 要求**：授权上下文是请求/命令作用域内的显式对象，不是全局可变状态；
异步任务必须显式传递身份与 scope。

---

## AUTH-03 所有权与活动绑定在锁后的行上判断

**规则**：任何“这条记录属于当前活动/当前用户”的判断，都必须在取得聚合锁
之后对**锁定行**重新求值，不能使用加锁前的读取结果。

**为什么**：加锁前的对象可能已经被并发修改、删除或换绑。v1 的票据、评委
入口、报名审核、结果发布都补过“锁后重读并重新验证”的 fix。

**必须攻击的形状**：

- 加锁窗口内把记录移到另一个活动；
- 加锁窗口内删除记录（锁后 `.get()` 变成 500）；
- 用另一个活动的 ID 伪造请求参数。

**Plus 要求**：command 的输入只包含 ID；锁后重新加载聚合并重新校验活动、
所有者、状态；不能把客户端传来的 activity_id 当作事实。

---

## AUTH-04 私有媒体只能经受控访问

**规则**：上传文件、生成文档、导出包、备份、结果海报等私有资产，只能通过
统一媒体网关按“请求者与这个对象的关系”授权后读取；不得挂静态路由或直接
暴露存储 URL。

**为什么**：v1 的 `controlled_media` 是唯一出口；修复过 `_base_manager`、
raw delete、conflict upsert 让媒体行被改写，以及正式结果撤销后自由封面/媒体
仍匿名可读。

**必须攻击的形状**：

- 匿名直接请求 `/media/<存储路径>`；
- 他人请求、跨活动请求；
- 结果 release 后请求 editorial 封面/媒体；
- 撤销/替代后仍能读到旧媒体；
- 路径穿越、符号链接、junction。

**Plus 要求**：媒体授权是对象级策略；URL 不包含可伪造的所有权；对象存储
只能通过短时签名或网关转发，私有 bucket 保持私有。

---

## AUTH-05 删除是领域命令；会销毁事实的级联需要显式清理 authority

**规则**：删除聚合不是“删一行”，而是“销毁一组事实”。普通路径不得级联删除
评分、投票、结果、票据等事实；只有显式清理命令（例如测试数据清理）可以按
受控顺序删除，并留下审计。

**为什么**：v1 的报名删除会 CASCADE 到评分类事实；清理顺序错误会触发
`ProtectedError` 并回滚整场彩排。测试数据清理后来成为唯一允许删除报名的
authority。

**必须攻击的形状**：

- 普通用户/工作人员删除报名或轮次；
- 清理命令遇到仍在使用的正式结果、投票或票据；
- 删除顺序违反 `PROTECT`；
- 测试数据与正式数据混在一起被清理。

**Plus 要求**：删除命令声明它会销毁哪些事实；引用方以 `RESTRICT`/显式检查
阻止误删；清理只对可证明的测试数据生效，并且可审计、可重放。

---

## AUTH-06 测试数据与正式数据是两条生命周期

**规则**：TEST 活动/数据不能被正式命令当作正式事实；正式结果发布、归档等
路径必须拒绝测试活动。测试清理只能删除可证明属于 TEST 的数据。

**为什么**：v1 多次出现“TEST 夹具证明了一条 FORMAL 会 500 的路径”；测试
清理与正式清理的删除集合不同，不能互相代替证据。

**必须攻击的形状**：

- 对 TEST 活动发布正式结果或归档；
- 在 FORMAL 活动上运行测试清理；
- 用测试数据充当正式 Golden；
- 手工改 `is_test_data` 后走正式路径。

**Plus 要求**：数据生命周期是聚合的显式字段；命令按生命周期分流；Golden
与彩排使用与生产相同的生命周期构造。

---

## AUTH-07 对外可见性不自动扩展到子资产

**规则**：父对象“可公开”不等于它的自由编辑资产（封面、正文、附件、上传
海报）都变成公开。公开面由 authority 明确命名的内容组成。

**为什么**：v1 曾出现：正式结果 release 后页面不展示 editorial 媒体，但媒体
网关仍因 post 属于 `published_public()` 而匿名返回旧海报；正式结果需要海报时
应该另建 release-owned 资产。

**必须攻击的形状**：

- ACTIVE release 后请求 result post 的 cover/PublicMedia；
- REVOKED/SUPERSEDED 后仍可访问旧资产；
- 用同一路径被普通公告共享时的边界；
- SSR 首屏、列表、PDF、归档各自泄漏不同字段。

**Plus 要求**：公开 read model 明确列出可公开字段；子资产有独立可见性；任何
“父可公开”的推导都不能自动放行自由资产。
