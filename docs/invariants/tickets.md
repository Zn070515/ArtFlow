# TICK — 票据、凭证、访问与限流

**原则**：公开的活动码不是凭证；凭证必须可验证、可失效、不可重放；访问
决策不能泄漏系统里存在哪些活动。

v1 证据：52 条票据/凭证/访问类 fix，高频词 `ticket 15`、`access 14`、`lock`。

---

## TICK-01 公开 code 与凭证分离

**规则**：活动 public code 只用于定位，不构成任何领票/评分/管理权限。需要
权限的动作必须持有独立签发、可验证的凭证（签名 token / capability）。

**为什么**：v1 的 `/e/<code>/judge/` 曾只要知道 activity code 就能认领真实
评委席位；修复为 fragment 中的 HMAC capability，版本从锁定行读取。

**必须攻击的形状**：

- 只用 public code 访问评委入口；
- 伪造/重放 capability；
- 用其他活动的 capability；
- 从 URL/Referer/日志中拿到 token。

**Plus 要求**：凭证是领域对象；签发、验证、失效都有明确命令；token 不进
服务端日志、不进 Referer、不落库。

---

## TICK-02 重新签发立即失效旧凭证；关闭入口只拒绝新领取

**规则**：reissue 递增版本，所有旧凭证立即失效；close 拒绝新的 claim，但
不驱逐已经领取的席位/会话。

**为什么**：v1 的评委入口与票据都补过“锁后重新验证 version”的竞态；否则
在 reissue/close 与 claim 之间的窗口里，旧码仍能领到席位。

**必须攻击的形状**：

- reissue 后旧码 claim；
- close 后新 claim；
- 已领取的会话在 close 后继续使用；
- 两把锁之间的并发窗口。

**Plus 要求**：凭证版本是行上事实；claim 在锁内重新验证；close 的语义是
“停止新增”，不是“清理现场”。

---

## TICK-03 领票/领席是“解析 → 锁定 → 重验 → 领取”

**规则**：先解析凭证以确定要锁的行；拿到行锁后，对锁定行重新校验凭证、
入口状态、席位可用性，再创建 claim。不能信任解析阶段的结果。

**为什么**：v1 的 `claim_judge_session_for_entry` 记录了这个顺序；此前 view
自己拼步骤，漏了重验。

**必须攻击的形状**：

- 解析后被 reissue/close；
- 解析后席位被他人抢走；
- 解析后被删除；
- 同一凭证并发 claim 两次。

**Plus 要求**：claim 是一个事务命令；输入只有原始凭证；内部完成解析、锁、
重验、分配；返回明确的拒绝原因码。

---

## TICK-04 票据身份决定投票唯一性

**规则**：需要票据的投票，一张票只能产生一票（或按规则的多选），唯一性由
ticket/ballot 身份保证；无票投票才使用浏览器身份，且只能作为弱约束。

**为什么**：v1 曾用浏览器指纹作为唯一性，导致同一人换浏览器重复投票；修复
为 ticket-backed ballot 唯一性，浏览器唯一性只在无票场景保留。

**必须攻击的形状**：

- 同一 ticket 重复投；
- 换浏览器/无痕重复投；
- 伪造 ticket 关联；
- 多选超出规则。

**Plus 要求**：投票身份是显式类型（ticket / browser / anonymous）；唯一约束
落在数据库；重复投票返回明确错误，不静默覆盖。

---

## TICK-05 凭证存储与传输最小化

**规则**：原始 token 不落库；只存哈希/签名；浏览器使用 HttpOnly cookie；
不在 URL query、日志、审计、导出中出现明文。

**为什么**：v1 的 ticket 凭证、评委 capability、access key 都按这个原则
处理；入口 token 放在 fragment，浏览器不会发给服务器。

**必须攻击的形状**：

- token 出现在访问日志/错误日志；
- token 存进数据库/导出；
- token 放在 query 被 Referer 泄漏；
- 重放响应缓存了凭证。

**Plus 要求**：token 只在内存/一次性响应中出现；存储是哈希；日志有脱敏器；
缓存策略 no-store。

---

## TICK-06 访问决策不泄漏“活动/席位是否存在”

**规则**：无效凭证与不存在活动对外表现一致（404）；只有持有有效凭证的人
才能看到“入口已关闭”“席位已满”等具体原因。

**为什么**：v1 的评委入口规定：凭证不解析 → 404；解析成功但关闭 → 409
`JUDGE_ENTRY_CLOSED`，让早到的老师知道该等，而不是去猜。

**必须攻击的形状**：

- 枚举 activity code 判断存在性；
- 用无效凭证探测席位状态；
- 通过错误码推断他人是否存在。

**Plus 要求**：错误码是能力感知的；未授权请求不返回资源存在性。

---

## TICK-07 限流是边界，不是可选项

**规则**：领票、评分、登录、上传等公共入口必须按 actor/IP 限流；限流
失败时 fail closed 或明确降级，不能静默放行。

**为什么**：v1 的登录、评委 claim、评分、上传都补过限流；缓存/进程隔离导致
测试里计数串扰，后来统一了 key 与清理。

**必须攻击的形状**：

- 同一 IP 枚举凭证；
- 同一 actor 高频提交；
- 限流状态在测试/重启后串扰；
- 限流后端故障时放行。

**Plus 要求**：限流器有明确语义（per-actor/per-IP/窗口）；key 包含租户/活动；
后端故障策略是显式的；测试会清理计数。
