# Production Delivery and Recovery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove runtime CDN dependence and provide a non-destructive, tested PostgreSQL backup/restore rehearsal.

**Architecture:** Build CSS during image/CI preparation and serve it through Django staticfiles. Add a PowerShell backup verifier that uses a separate restore database/container and never resets the source Compose volume. Keep release contracts in documentation and CI checks.

**Tech Stack:** Tailwind CSS 3 pinned with npm lockfile, Django `collectstatic`, PowerShell, Docker Compose, PostgreSQL `pg_dump`/`pg_restore`, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-27-production-correctness-hardening-design.md`

## Global Constraints

- Deployed HTML must not load Tailwind or CSS from a public runtime CDN.
- Generated CSS is reproducible from a pinned lockfile and collected by Django.
- Backup verification never drops, resets, or mutates the source database or named volumes.
- Restore validation runs against a separate database target and includes Django checks plus read-only integrity queries.
- Existing CI, Compose acceptance, docs checks, and coverage gates remain green.

### Task 2: Add safe PostgreSQL backup creation and restore verification

**Files:**
- Create: `scripts/verify_postgres_backup_restore.ps1`
- Create: `scripts/verify_postgres_backup_restore.Tests.ps1` if Pester is available, otherwise extend the existing verifier tests
- Modify: `scripts/verify_postgres_acceptance.ps1`
- Modify: `docker-compose.yml` only to expose a separate temporary restore service/network when required
- Modify: `.github/workflows/integration.yml`
- Modify: `docs/operations.md` or create `docs/postgres-backup-restore.md`

**Interfaces:**
- `verify_postgres_backup_restore.ps1 -BackupPath <path> -ComposeProjectName <name> -RestoreDatabase <name>` creates a custom-format dump from the running source `db`, validates it with `pg_restore --list`, restores into a separate temporary PostgreSQL database/container, runs `python manage.py check`, and executes read-only counts/integrity queries.
- The script rejects a backup path outside the requested output directory and never invokes `down -v`, `reset`, `dropdb` on the source, or destructive Compose commands.

- [ ] **Step 1: Write failing script-verification tests** for missing backup, empty backup, invalid restore target, and source-volume-preservation assertions.
- [ ] **Step 2: Run the script/verifier tests and verify the new command is absent or the safety checks fail.
- [ ] **Step 3: Implement source dump, `pg_restore --list` validation, isolated restore target creation, Django check, read-only integrity query, and finally-only temporary target cleanup.
- [ ] **Step 4: Add a Compose acceptance invocation that leaves the source services/volumes intact and records the backup artifact.
- [ ] **Step 5: Run the script with Docker when available; when Docker is unavailable, run static safety checks and report the runtime limitation without claiming restore success.
- [ ] **Step 6: Commit with `git commit -m "feat: add postgres backup restore rehearsal"`.
