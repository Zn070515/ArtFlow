# 2026 校园十佳现场赛制：正式闭环改造说明

## 1. 文档目的

本文将 `C:\Users\16275\Desktop\advices\ChatGPT.md` 的审查意见固化为 ArtFlow 的可执行业务规格。目标不是做演示页面，而是让非开发工作人员能够在正式彩排和比赛日完成：报名材料确认、第一轮分组、连续挑战、最终十强确认、第三轮冠军赛及结果交接。

本文是业务约束和验收口径；实现计划见同目录的 `plans/2026-10-13-artflow-2026-live-rebuild.md`。

## 2. 不可变业务口径

### 2.1 赛制

- 第一轮共 15 人，5 组，每组 3 人。组内共享一首歌曲、伴奏和材料，但评委仍逐人评分。
- 第一轮由工作人员逐组开启评分。前一组仍可有未提交评分时，工作人员可以开始下一组；已开启的前一组允许评委之后补交。
- 每名选手达到本轮最低有效评委数后，只代表“可结束收分”，不会自动锁定；工作人员必须显式结束收分、锁定并确认。
- 第一轮产生初始十个席位和五名挑战者。挑战者按第一轮正式排名从低到高固定进入挑战队列，后续结果不得改写队列顺序。
- 每个初始席位最多被挑战一次；挑战者在配对确认前可以放弃，不消耗席位机会；配对确认后不提供普通撤回，只走异常暂停/管理员记录。
- 挑战者口头选择对手，由工作人员在控制台记录并确认。挑战者先演出，守擂者后演出；两边达到最低有效评委数即可分别锁定，评委集合不要求相同。
- 每场挑战使用第一轮和第二轮已经确认的正式成绩及配置权重，权重合计 100%，决定席位保留或替换。胜者继承守擂者的席位/第三轮位置。
- 五个挑战机会全部处理后，挑战会话的十个席位就是最终十强。第三轮按**席位顺序**出场，不按官方编号重排：第 1–10 号位置在建立挑战会话时就已按官方编号固定，踢馆成功者继承被挑战守擂者的位置。冠亚季军按冻结的「冠亚季军第一轮权重」与「冠亚季军第三轮权重」对第一轮和第三轮正式成绩加权，挑战场次比分不进入该加权。
  - 修订说明（2026-10-15）：本行原写作“第三轮固定按官方选手编号升序出场，第三轮成绩单独决定冠亚季军”，已被后续决策取代。实现见 `singer_contest/challenge_services.py::create_final_round_from_challenge()`（席位顺序 + 人工顺序）与 `singer_contest/podium_services.py::build_podium_result()`（第一轮/第三轮加权）；决策记录见 `plans/2026-10-14-live-challenge-audit-complete.md`；现场口径见 `docs/production-rehearsal-runbook.md`。

### 2.2 成绩、并列和权限

- 三轮使用同一评分量表、评分项、满分和权重；每轮可单独配置评委、评委人数和最低有效评委数。
- 正式分数是所有有效评委分数的算术平均，使用 `Decimal`、`ROUND_HALF_UP`、量化到两位小数。挑战复合分使用已确认的第一轮/第二轮两位小数成绩，再量化到两位小数。
- 排名、晋级、挑战胜负只使用已确认的两位小数正式成绩。缺失成绩绝不能当作 0。
- 本次赛制不设计加赛、评委投票、隐藏 ID 排序或其他自动破平规则。真实计算结果相等时，系统必须阻止自动确认并要求工作人员处理数据异常。
- Staff/Admin 都可以执行日常确认；只有 Admin 可以执行高风险解锁、撤销和更正。所有命令带 `command_id` 和版本，所有正式事实带审计记录。

## 3. 当前基线与必须修正的问题

当前基线为 `66461d7c1a4831c569a139ab9045dc06184d5019`。审计已确认：

1. `prepare_judge_panel()` 的匿名评委分支把 `judge_count` 当成最低有效人数，忽略了 `minimum_judge_count`。
2. `lock_round()` 要求完整评分矩阵，`_recalculate_round()` 遇到任意缺失即清空汇总；需要新增明确的“最低有效评委数”完成语义，同时保留历史全矩阵轮次。
3. `ScoreSummary.average_score` 保存三位小数，汇总和规则解析器使用未量化平均值；必须建立单一评分核心，消除排序和加权时的精度漂移。
4. 评委提交只接受 `PerformanceRunState.current_performance_id`，推进到下一名后，已开启但未提交的前一名无法补交；必须增加独立的逐表演开启状态，不能把所有表演预先开放。
5. `SingerRegistration.pk` 不是官方选手编号；十个席位的**初始位置**必须依赖活动内唯一、受控、冻结的官方编号（第三轮出场顺序此后由席位继承决定，不再按编号重排）。
6. 现有 `PAIR/DUEL` 和完整 `ContestRound` 不能直接表达五次连续挑战；需要独立的挑战会话、挑战顺序、席位、配对和比赛确认 authority。

## 4. 目标领域模型

### 4.1 评分核心

评分核心提供四个唯一入口：

- `quantize_official_score(value)`：两位小数、`ROUND_HALF_UP`；
- `score_completeness(...)`：区分未开启、已开启但不足最低人数、达到最低人数、已锁定；每名选手独立计算；
- `official_average(scores, scoring_mode)`：只对有效成绩求平均，缺失不补零；
- `official_weighted_score(components, weights)`：只接受已经确认的正式分数并再次量化。

旧轮次默认保持完整矩阵语义；新赛制显式声明最低有效人数语义。冻结后的面板快照保存最低人数，解析器和工作人员服务都读取同一快照。

### 4.2 Live Challenge

独立模块至少包含：

- `ChallengeSession`：活动、当前冻结规则版本、第一轮确认结果、输入指纹、修订号和状态；
- `ChallengeTurn`：五名挑战者的固定顺序、是否已放弃、当前处理状态；
- `ChallengeSeat`：十个席位、初始持有人、当前持有人、第三轮位置、是否已被挑战；
- `ChallengeMatch`：挑战者、守擂者、席位、第一/第二轮成绩引用、双方评分单元、锁定版本、正式胜负和确认状态。

数据库事务必须保证：同一时刻只有一个可操作挑战位；不能跳过前一位；一个挑战者只能产生一次有效配对；已挑战席位不能再次选择；每次确认后恰有十个不同席位持有人；并发工作人员不能产生两个正式结果；确认后的比赛不可直接修改。第一轮更正、冻结规则变化或输入指纹变化必须阻止复用旧挑战数据。

挑战比赛的实际评分单元可以复用 `ScoreRecord`、面板快照、席位权限和收分回执，但不能把五场挑战塞成一个要求完整 15 人矩阵的普通评分轮次；每场必须是严格两人，弃权不制造假的缺失成绩。

### 4.3 材料和冻结

- 第一轮使用分组合唱材料，组员可查看同一份材料。
- 第二轮预先收集 15 份个人歌曲/伴奏材料；第三轮也预先收集 15 份个人歌曲/伴奏材料，不能等晋级后才提交。
- 材料继续复用 Questionnaire/文件检查 authority；工作人员可按第一轮分组、第二轮个人、第三轮个人查看完成度和历史，受控补交不能绕过文件校验、EXIF 清理、审计和事务补偿。
- 规则冻结页只暴露业务语言：人数/分组、统一评分表、各轮评委及最低人数、挑战权重、确认后的对手和顺序。权重必须显式合计 100%；草稿可以不完整，冻结必须完整。

## 5. 工作人员操作台

控制台只回答“现在在哪里、轮到谁、下一步做什么”，不显示 `Ruleset/PAIR/DUEL/StageResult/fingerprint/binding` 等内部术语。核心状态和动作如下：

| 现场状态 | 主动作 |
| --- | --- |
| 第一轮全部达到最低人数 | 确认第一轮 |
| 等待下一名挑战者 | 开始下一次选择 |
| 挑战者选择中 | 记录目标 |
| 目标已选 | 确认配对 |
| 挑战者演出结束 | 开启挑战者评分 |
| 守擂者演出结束 | 开启守擂者评分 |
| 双方达到最低人数 | 结束并锁定 |
| 等待胜负确认 | 确认胜负 |
| 比赛已确认 | 显示交接提示/告知主持人 |
| 五次机会全部处理 | 确认最终十强 |
| 第三轮已结束 | 确认冠亚季军 |

合法对手必须由后端给出，并对已挑战席位、重复目标、未到选择阶段等非法选项给出原因。任何 Staff/Admin 都可以接管，不绑定固定工作人员；异常路径进入管理员修正区；不做主持人大屏和公开实时成绩广播。

## 6. 验收场景

至少覆盖以下 18 项：

1. 15 人、5 组×3 人，组内独立评分；
2. 前组未完成时后组可开启，前组可迟交；
3. 5 名评委、最低 4 人时，每名选手可使用不同的 4 名有效评委；
4. 达到最低人数不自动锁定，人工锁定后拒绝新评分；
5. `ROUND_HALF_UP` 两位小数贯穿汇总、排名和挑战加权；
6. 第一轮确认生成固定挑战顺序和十个席位；
7. 配对前放弃会推进队列且不消耗席位；
8. 已确认比赛的席位不可再次被挑战；
9. 挑战者先开评分，守擂者后开评分，双方独立完成；
10. 五次机会完成后正好十名唯一持有人；
11. 胜者继承守擂者第三轮位置；
12. 冠亚季军名次由冻结的第一轮/第三轮加权成绩决定，挑战场次比分不参与；
13. Staff/Admin 可日常确认，只有 Admin 可高风险解锁；
14. 并发选择、锁分、确认不产生双写或 500；
15. 重试命令幂等；
16. 第一轮更正/确认比赛撤销触发下游保护；
17. Redis/WebSocket 故障不影响 HTTP authority；
18. 任何正式成绩相等时阻止自动确认。

## 7. 分阶段交付

1. 评分核心、最低有效评委数和人工锁分；
2. 逐表演开启、迟交和裁判端“当前/待提交”视图；
3. 官方选手编号和冻结/更正 authority；
4. Live Challenge 状态机、并发、幂等、指纹和席位；
5. 动态两人评分单元及结果闭环；
6. Questionnaire 材料投影和受控补交；
7. 简单工作人员操作台；
8. PostgreSQL、权限、真实浏览器和完整彩排验收。

每阶段都要先写失败测试，再实现，再跑相应门禁；每个逻辑改动保持独立提交。完成标准是：非开发工作人员不看技术文档也能完成正式彩排，评委无需重复扫码，所有决定可追溯、可重放、可解释。

## 8. 明确不在本次范围

- 不做 ArtFlow-Plus 或商业化大重写；
- 不添加自动破平、加赛、评委临时投票或隐藏排序；
- 不把 Redis/WebSocket 变成成绩权威；
- 不用模板默认值覆盖冻结规则；
- 不以 UI 伪造挑战流程，不绕过现有文件、权限、审计、锁定和事务补偿边界。
